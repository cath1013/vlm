# 재실험 전에 알아야 할 것

[01](01-prediction-horizon.md)·[02](02-what-helps.md)의 결과를 내는 과정에서 밟은
함정과 확인한 것들. **여기 적힌 것을 모르고 다시 실험하면 엉뚱한 것을 재게 된다.**

각 항목은 **대상 데이터가 다르다.** 항목마다 적어 두었다.

---

## LLM 은 같은 입력에 다르게 답한다

*대상: 시나리오 1개, 창 4개, `claude-opus-5`, 2026-08-04 에 저장된 응답*

2026-08-04 실험이 예측기 3종을 비교해 정확도 0.643 → 0.679 → 0.714 를 얻었다. 그럴듯해
보이지만, 실제로 바뀐 것은 **오탐 (false positive) 이 8 → 7 → 6**, 즉 판정 하나씩이었다.

`out/llm_responses_archive/rule_run2` 는 정확히 이 질문을 위해 **같은 입력을 두 번째로
호출해 둔** 것이다. 겹치는 창 4개(구간 20개)를 비교하면:

| 비교 | 다르게 답한 구간 / 20 | 일치율 |
|---|---:|---:|
| **같은 입력, 두 번 호출** | **3** | 0.850 |
| 예측기를 rule → waypoints | **3** | 0.850 |
| 예측기를 rank → waypoints | 4 | 0.800 |
| 예측기를 rule → rank | 5 | 0.750 |

**예측기를 바꾼 것과 같은 입력을 두 번 부른 것이 구별되지 않는다.** 둘 다 "사고"라고
답한 구간 5개 중 2개는 관련 차량마저 다르게 지목했다.

손으로 확인한 사례 — 창 `0-1`, 구간 k=3, **완전히 같은 입력**:

> **1차:** 사고 있음, `[EGO_other_vehicle, V016]` — "현재 가속을 유지하면 약 3.3s 후 …"
> **2차:** 사고 없음 — "두 차량 간 거리 30m 이상이며 … 간격도 아직 15m 이상 남 …"

**시사** — 예측기나 프롬프트를 비교하려면 **같은 조건을 여러 번 돌려야 한다.** 규모를
키울 때 일부 시나리오를 2~3회 중복 호출해 이 흔들림의 크기를 함께 재야 한다.

이 흔들림의 상당 부분은 [01](01-prediction-horizon.md) 로 설명된다 — 위 측정의 판정
20개 중 **12개(60%)가 k=3~5**, 즉 어떤 방법으로도 우연 수준인 구간에서 나온다.
(val 전체로 보면 k=3~5 가 46% 다.)

```bash
.venv/bin/python examples/llm_noise.py out/llm_responses_archive
```

정답이 필요 없다 — 두 응답을 서로 비교할 뿐이므로, 그 사이 payload 가 바뀌어
재채점이 불가능해진 것과 무관하게 측정된다.

## 모델이 산술을 할 수 있는지 먼저 재라

*대상: 합성 문제 (데이터셋 안 씀), 로컬 GPU*

`~/vlm` 은 본 실험 전에 "이 모델이 조감도에서 위치를 짚을 수 있나"를 먼저 쟀고
(`probe_bev_localise.py`), Qwen3-VL-8B 는 9개 중 1개였다. 같은 리포트가 이렇게도 적었다:

> 같은 모델들이 **두 물체 사이 거리 계산도 못 한다** — 4.5m 떨어진 행이 있는 표를
> 주고 "30m 안에 움직이는 물체가 없다"고 답했다.

`examples/probe_capability.py` 는 그 텍스트판이다. 문제를 직접 만들어 내므로 정답이
확실하고 데이터셋이 필요 없다. 각 8문항:

| 문제 | 재는 것 | Qwen3-VL-8B | Qwen3-VL-32B |
|---|---|---:|---:|
| `read` | 상태표에서 값 하나 읽기 | **1.00** | **1.00** |
| `distance` | 좌표 두 개 → 거리 | **0.12** | 0.38 |
| `extrapol` | 위치·속도 → N초 뒤 위치 | 0.38 | 0.50 |
| `closest` | 여러 대 중 가장 가까운 쌍 | 0.50 | 0.75 |
| `detect` | 위험한 장면을 위험이라 하는가 | 0.62 | **0.00** |
| `ruleout` | 안전한 장면을 안전이라 하는가 | 0.50 | **1.00** |

**표는 읽는데 산술을 못 한다.** 그리고 32B 는 판정 16문항을 **전부 "안 부딪힌다"** 로
답했다 — 정면 21m 앞에서 초속 20m 로 다가오는 차를 보고도 그렇다. 문제가 애매한 것이
아니다. 기하를 수치로 검산했다: 약 1.05초 뒤 중심거리 0.0~0.3m, 확실한 충돌이다.

같은 32B 가 실제 과제(차 26대가 있는 장면)에서는 **정반대로** 5개 구간 전부 "사고"라고
답했다. 계산해서 답을 바꾸는 것이 아니라 **장면이 복잡하면 위험 쪽, 단순하면 안전 쪽으로
쏠린다.**

**시사** — 로컬 Qwen 으로 규모를 키우는 것은 의미가 없다. 몇 시간을 써서 같은 답을
1,000번 받게 된다. `gemini-2.5-flash` 는 vlm 이 시험한 모델 중 "아니오"를 할 수 있었던
유일한 모델이고, 그 순위가 입력 방식(이미지냐 텍스트냐)과 무관하게 전이된다.

```bash
~/vlm/.venv-qwen/bin/python examples/probe_capability.py --model <모델> --n 8
```

## 정답이 새고 있지 않은지 확인하라

*대상: `traffic_llm` payload 49개 전수*

DeepAccident 에는 **거의 완벽한 지름길이 둘** 있다 (`~/vlm/bev_report.md` §4):

| 지름길 | 강도 |
|---|---|
| **클립 길이만으로** | **AUC 0.983** — 사고 클립은 충돌에서 끊겨 59프레임, 대조군은 96 |
| **폴더 이름만으로** | val 정확도 **0.971** |

즉 영상을 아예 안 보고 "이 클립이 몇 프레임인가"만 세도 98% 를 맞힌다. 프롬프트에
그런 것이 섞여 들어가면 실험이 무의미해진다.

`traffic_llm` payload 49개를 전수 검사한 결과 **둘 다 들어가지 않는다**:

```
시나리오 이름 0/49 · 사고|정상 폴더명 0/49 · 전체 프레임 수 0/49 · 녹화 길이 0/49
질문이 묻는 구간 수: 전부 5개로 고정
```

설계상 분리되어 있다 — 모델이 보는 쪽(`ScenarioContext.available`)에는 날씨와 도로
형태만 있고, 충돌 위치·방향 같은 것은 정답 쪽(`ground_truth`)으로 격리된다.

**다만 이것은 지금까지 확인된 적이 없었다.** payload 를 바꿀 때마다 다시 봐야 한다.

## 두 프로젝트는 이미 맞물린다

*대상: val 104 시나리오*

`traffic_llm` 과 `~/vlm` 은 서로를 모르고 작성됐는데 네 층이 이미 맞는다.

| 층 | 확인 |
|---|---|
| **좌표계** | iitp 의 위치값 = CARLA 월드 좌표, **차이 0** (소수점까지 같다) |
| **신원** | 양쪽 다 CARLA 가 부여한 차량 번호를 쓴다 |
| **시나리오 이름** | `type1_…/Town05_…` ↔ `type1_…__Town05_…` (구분자만 다름) |
| **정답 라벨** | 사고 여부·방향·충격 부위·당사자 번호·클래스쌍 **104/104 일치** |

정답 라벨은 iitp 가 `meta` 파일 첫 줄을, vlm 이 자기 코드로 각각 따로 읽은 것이다.
104개가 하나도 안 어긋났다.

**시점 맞추기** — vlm 의 판단 시점은 `마지막 프레임 − (몇 초 앞 ÷ 0.1)` 이고 과거
1.0초를 0.5초 간격 3프레임으로 본다. iitp 의 기존 창을 재활용하면 최대 0.5초 어긋나지만
(창 끝이 0.5초 격자에 떨어지므로), **그 프레임들만 지정해 창을 새로 만들면 차이가 0** 이다.

```bash
.venv/bin/python examples/export_scene_for_vlm.py --split val --horizon 1.0 --lang en
```

## 실제로 밟은 함정들

**정확도만 보면 속는다.** 사고가 10.9% 뿐이라 아무 말도 안 하면 정확도 0.876 이 나온다.
균형정확도로 보면 0.5 다. 같은 이유로 **임계값을 F1 으로 고르면 안 된다** — train 에서
사고 154개를 맞히는 대신 오탐 1,644개를 내는 값이 뽑힌다.

**중심끼리의 거리를 접촉 기준으로 쓰면 안 된다.** 정답 데이터의 기준("두 차 길이의
절반 합 + 여유 2m")은 *이미 알려진 충돌 쌍*의 가장 가까운 순간을 찾는 용도다. 모든 쌍에
적용하면 승용차 둘이 6.6m 라 차선에 줄 서 있는 차가 전부 접촉으로 잡힌다 — 구간의
64% 에서 발동했다. **회전한 사각형끼리의 실제 간격**을 써야 한다.

**등속으로 밀면 차가 서로를 통과한다.** 마주 오는 두 차를 4초 밀면 간격이
`[15.4, 0, 0, 17.4]` 로 나온다 — 겹쳤다가 지나쳐 다시 벌어진다. 실사용에는 문제가
없다(정답도 충돌에서 녹화가 끊기고 그 뒤는 채점에서 빠진다). 다만 모르고 읽으면
"충돌 후 안전해졌다"로 오독한다.

**WaypointNet 의 웨이포인트는 첫 점이 현재 위치다.** t=1 부터라고 가정해 현재 위치를
앞에 덧붙이면 전체가 1초씩 밀린다. 그리고 차량의 **약 24% 는 점이 1개뿐**이다
(도로 끝에서 잘렸거나 정지 상태) — 처리를 안 해 두면 시나리오 전체가 오류로 죽는다.

**영어로 뽑아도 한글이 샌다.** WaypointNet 이 라벨을 조합해서 만들기 때문에
(`후보 밖 경로(가장 가까운 기동 {maneuver})` — 코드에 그대로 박힌 문자열이다) 사전
조회로는 안 걸린다. `--lang en` 으로 뽑은 val 104개 중 **96개에 323회** 남아 있었다.
그대로 실험했으면 "정보의 효과"가 아니라 "한영 혼용의 효과"를 잴 뻔했다. 지금은
번역기가 조합 라벨을 재귀적으로 풀고, 테스트가 그것을 고정한다.

기하 계산은 **손으로 답을 알 수 있는 배치**로 고정되어 있다 — 회전시켜도 넓이가
보존되는지, 축에 나란한 상자로는 겹치지만 실제로는 떨어진 45° 대각 배치를 구분하는지,
겹치거나 닿으면 0 이 나오는지, 좌우를 바꿔도 같은지, 직교로 들이받는 배치,
웨이포인트 정렬 두 규약, 예측이 없을 때 등속으로 되돌아가는지.

```bash
DEEPACCIDENT_ROOT=/home/sryu/inclab-nas/DeepAccident/DeepAccident_mini \
    .venv/bin/python -m unittest discover -s tests     # 537개
```

# LLM payload — 자연어 설명 부분의 구조

사고 예측 payload 의 **자연어 브리핑**이 어떤 절로 구성되고, 각 절이 어떤 형식으로
무엇을 담는지 정리한다. 구조화 JSON 블록은 기본으로 들어가지 않으므로
(`include_json_block=False`) **이 자연어가 모델이 보는 유일한 상황 설명**이다.

모듈별 알고리즘은 [`payload_modules.md`](payload_modules.md) 에 있다.

---

## payload 전체 구성

```
요청 본문
├─ system 프롬프트          약 1.6K자   ← 역할·데이터 규약·판단 원칙
└─ 사용자 메시지
   ├─ [블록 1] 자연어 브리핑  약 23K자   ← 이 문서의 대상
   ├─ [블록 2] 구조화 JSON   (기본 없음)
   └─ [블록 3] 질문          약 0.7K자   ← 구간 정의·답변 규칙
```

Town05 윈도우 3-8 실측: 총 25,614자(평균). Claude 는 세 블록을 그대로 유지하고,
OpenAI 는 사용자 블록을 한 문자열로 합치며, Gemini 는 `parts[]` 로 유지한다 —
**내용은 provider 와 무관하게 같다.**

---

## 블록 1 — 자연어 브리핑의 절 구조

절이 나오는 순서와 역할이 정해져 있다. **넓게 → 좁게, 과거 → 현재** 순이다.

| # | 절 | 답하는 질문 |
|---|---|---|
| 0 | 머리글 | 이 윈도우가 언제이고 무엇이 몇 대 있는가 |
| 1 | `## 노변 인프라 센서` | 고정 센서가 어디에 있는가 (교통 참여자 아님) |
| 2 | `## 관측 관계` | 누가 누구를 인지했는가 |
| 3 | `## 차량별 시간 경과` | 각 차량이 어떻게 여기까지 왔는가 |
| 4 | `## 윈도우 동안 서로 접근한 차량 쌍` | 누가 누구에게 접근하는가 |
| 5 | `## 마지막 관측 시점 상세` | 지금 무엇이 어디에 있는가 |
| 6 | `## BEV 개략도` | 공간 배치가 어떻게 생겼는가 |

5번 절은 안에 다시 `## 관측차량` / `## 주변차량` / `## 노변 인프라 센서` /
`## 상호작용 및 주의 상황` 을 갖는다 (단일 스냅샷 브리핑 `to_text()` 를 그대로
끼워 넣기 때문이다).

---

## 0. 머리글

```
# 관측 윈도우 3-8 (t=3~8초, 스냅샷 11개)
배경: 출처 DeepAccident, 지도 Town05, weather=ClearNight, road_type=three-way junction
마지막 시점 기준 관측차량 4대, 주변차량 22대, 노변 인프라 1기
```

- **윈도우 라벨** `3-8` 은 파일명(`llm_payload_3-8.json`)과 정답 파일에 그대로
  쓰이는 키다.
- **배경**은 주행 시점에 알 수 있는 정보만 담는다. 시나리오 id 는 분할명
  (`..._accident`)을 담아 정답이 새므로 **넣지 않는다**.
- 대수는 **마지막 시점 기준**이다. 윈도우 중간에만 보인 차량이 있어 3번 절의
  차량 수와 다를 수 있다.

---

## 1. 노변 인프라 센서

```
## 노변 인프라 센서 (V2X, 교통 참여자 아님)
- infrastructure: 설치높이 3.6m, 이 시각 관측 15건
```

절 제목에 **"교통 참여자 아님"** 을 박아 둔다. 인프라를 차량 목록에 섞으면 모델이
존재하지 않는 정차 차량으로 오해한다. 도로에 매칭되면 `<도로> 인접`, 지향 방위가
있으면 `지향 <각>°` 가 붙는다.

---

## 2. 관측 관계 — 누가 누구를 인지했는가

```
## 관측 관계 (누가 누구를 인지했는가)
- ego_vehicle(차량): 12대 인지 | 본체 액터 id EGO_ego_vehicle | 카메라 6대 360° 커버
- ego_vehicle_behind(차량): 17대 인지 | 단독 인지 N011, T012, V013 | 본체 액터 id EGO_ego_vehicle_behind | 카메라 6대 360° 커버
- infrastructure(인프라): 15대 인지 | 카메라 6대 360° 커버
```

| 항목 | 뜻 |
|---|---|
| `<이름>(차량\|인프라)` | 관측자 id 와 종류 |
| `N대 인지` | 마지막 시각에 인지한 차량 수 (**자기 자신 제외**) |
| `단독 인지 …` | 이 관측자가 **혼자** 본 차량 = 남의 사각지대를 메운 몫 |
| `본체 액터 id …` | 이 관측자 **차량 자체**의 액터 id |
| `카메라 N대 M° 커버` | 탑재 카메라 수와 덮는 방위 범위 |

### 왜 이 절이 있는가

액터별 "누가 나를 봤는가"를 **관측자 기준으로 뒤집은** 것이다. 파생 가능한 정보를
중복해 담는 이유는, 이 역변환이 V2X 추론의 핵심인데 차량 수십 대에 흩어진 관계를
모델이 직접 뒤집으면 자주 틀리기 때문이다.

**"인지 목록에 없다 = 그 시각에 못 봤다"** 가 사고 예측에서 중요한 이유: 물리적으로
충돌 경로에 있어도 당사자가 서로를 못 보고 있으면 회피 조작을 기대할 수 없다.

`카메라 … 커버` 가 그 미관측을 해석하는 열쇠다 — **360°를 덮는 관측자가 못 본 차량은
화각 밖이 아니라 가려진 것**이다. 커버리지는 화각의 **합집합**이라 6대 × 70° 여도
360°를 넘지 않는다.

### `본체 액터 id` 가 필요한 이유

관측자 이름(`ego_vehicle`)과 그 차량의 액터 id(`EGO_ego_vehicle`)는 **다른
문자열**이다. 이 매핑이 없으면 모델이 답변에 관측자 이름을 써서 차량 지목이 전부
오답 처리된다 — 실제 호출에서 그랬다. 인프라는 교통 참여자가 아니므로 본체 액터가
없고 이 항목이 붙지 않는다.

## 3. 차량별 시간 경과

차량마다 소절(`###`)을 만들고, 그 안에 시각별 한 줄을 넣는다.

```
### V013 (car) — 관측: ego_vehicle_behind, 존재확신 0.83, 관측거리 69m
   t=    3  (   76.2, -145.4)    26km/h  Road 20 동행 1/1차선 교차로 181m  차선유지
   t=    4  (   83.2, -144.8)    28km/h  Road 20 동행 1/1차선 교차로 174m  차선유지
```

### 소절 머리글

`### <액터 id> (<역할 또는 클래스>) — 관측: <관측자 목록>[, 존재확신 X.XX][, 관측거리 Nm]`

관측차량은 `(관측차량)`, 그 외는 클래스(`car`/`truck`/`person`/`van`/…)가 붙는다.
존재확신·관측거리는 주변차량에만 붙는다(관측차량은 자기 자신이므로 원격 관측이
아니다).

### 시각별 행 — 고정 폭 8열

```
   t=    3  (   76.2, -145.4)    26km/h  Road 20 동행 1/1차선 교차로 181m  차선유지
   └─시각   └─ENU 위치 (e, n)    └─속도  └─도로 └─방향 └─차선 └─교차로거리 └─기동
```

| 열 | 형식 | 비어 있을 때 |
|---|---|---|
| 시각 | 윈도우 시작을 기준으로 한 상대 초 | — |
| 위치 | `(e, n)` ENU [m], 소수 1자리 | — |
| 속도 | `NNkm/h` | ` 미확정 ` (정지가 **아니다**) |
| 도로·방향 | `<도로명> <8방위>` | `도로 미매칭` |
| 차선 | `<번호>/<총수>차선` | `차선미정` |
| 교차로 | `교차로 Nm` (150m 이내만) | 생략 |
| 기동 | `차선유지`/`가속 중`/`좌회전 중`/… | `미확인` |

**표본 간격은 `history_stride_s`(기본 1초)** 다. 스냅샷은 0.5초 간격 11개지만 행은
1초 간격 6개다 — 토큰 절약을 위해 솎아내고 마지막 시각은 항상 포함한다.

> 이 절이 **가장 길다** — 실측 13,614자로 브리핑 23,456자의 58%다. 차량 수 × 시각
> 수로 늘어나므로 토큰을 줄일 첫 지점이다: `--history-stride 2` 로 행을 반으로
> 줄일 수 있다.

절별 실측 크기 (Town05 윈도우 3-8, 차량 26대, 브리핑 23,456자):

| 절 | 크기 | 비중 |
|---|---|---|
| 차량별 시간 경과 | 13,614자 | 58% |
| 주변차량 (5-2) | 5,220자 | 22% |
| 접근한 차량 쌍 | 1,648자 | 7% |
| BEV 개략도 | 1,229자 | 5% |
| 관측차량 (5-1) | 469자 | 2% |
| 관측 관계 | 425자 | 2% |
| 상호작용 | 311자 | 1% |
| 나머지 (머리글·인프라·지도 규약) | 530자 | 2% |

## 4. 윈도우 동안 서로 접근한 차량 쌍

```
## 윈도우 동안 서로 접근한 차량 쌍
- EGO_ego_vehicle_behind ↔ P008: 거리 58.7m → 6.3m (접근율 10.5m/s, 선형연장 접촉까지 0.6s)
- EGO_other_vehicle_behind ↔ V002: 거리 49.5m → 8.4m (접근율 8.2m/s, 선형연장 접촉까지 1.0s, 동일 도로)
```

접촉이 이른 순으로 정렬한다. `동일 도로` 는 두 차량이 같은 도로에 매칭됐다는 표시로,
추종 상충과 교차 상충을 구별하는 단서다.

절 끝에 반드시 이 주의가 붙는다.

> `선형연장` 값은 관측된 거리 변화율을 그대로 늘린 것이며 회전·제동·신호를 반영한
> 경로 예측이 아닙니다.

### 몇 쌍이 나오는가

**관측된 차량 수에 맞춰 정한다** — 차량 수 × 0.5 (하한 6, 상한 20). 고정 상한을 쓰면
관측이 늘어날수록 담는 비율만 줄어, 실제로 사고 당사자 쌍이 목록 밖으로 밀려난 적이
있다.

여기에 순위와 무관한 안전장치가 있다: **접촉이 임박한 쌍(지평의 절반 = 2.5초 이내)은
상한을 넘겨도 담는다.**

## 5. 마지막 관측 시점 상세

```
## 마지막 관측 시점 상세 (t=8초)
배경: 출처 DeepAccident, 지도 Town05, weather=ClearNight, road_type=three-way junction
관측차량 4대, 주변차량 22대, 노변 인프라 1기 (전체 차량 26대 중 상위 26대 수록)
※ 지도 규약: 우측통행 | 1차선은 중앙선쪽 | 차선폭 3.50m | 도로 256개·교차로 76개
```

### 지도 규약 줄

| 항목 | 값 | 왜 필요한가 |
|---|---|---|
| 통행측 | `우측통행` / `좌측통행` | 좌/우 표현과 통행 차로 판정의 기준 |
| 차선번호 기준 | `1차선은 중앙선쪽`(한국) / `가장자리쪽`(미국식) | 모르면 차선 번호를 반대로 읽는다 |
| 차선폭 | `3.50m` | 횡방향 여유를 차로 단위로 환산할 때 |
| 지도 규모 | 도로·교차로 수 | 지도 밖 판단을 억제 |

도로지도가 궤적에서 합성된 경우 `※ 도로지도 출처: 궤적 합성 …` 줄이 함께 붙는다.

### 5-1. 관측차량 / 5-2. 주변차량

한 줄에 한 대. 파이프(`|`)로 구분한 항목의 **순서가 고정**되어 있다.

```
- V010(car): Road 20 서행 1차선 중 1차선 | 제한속도 56km/h | 다음 교차로까지 20m
  | 9km/h | 방위 271° | 차선유지 | 예상경로: 직진
  | 관측: ego_vehicle, … (존재확신 1.00, 위치정확도 1.00, 관측거리 19m)
  [EGO_ego_vehicle 기준 전방 12m, 좌측 3.4m]
```

| 순서 | 항목 | 비고 |
|---|---|---|
| 1 | `<도로명> <방향> <차선>` | 방향이 미확정이면 `(진행방향 미확정)` 이 붙는다 |
| 2 | `제한속도 Nkm/h` | 지도에 있을 때만 |
| 3 | `다음 교차로까지 Nm` | 150m 이내만 |
| 4 | `Nkm/h` | 속도. 미확정이면 그 표기 |
| 5 | `방위 N°` | 진북 기준 시계방향 |
| 6 | `±N.Nm/s²` | 가감속. \|0.5\| 초과일 때만 |
| 7 | 기동 | `차선유지`/`정지`/`가속 중`/… |
| 8 | `예상경로: …` | 후보 1개면 라벨만, 여럿이면 상위 3개 `기동 NN%` |
| 9 | `관측: <관측자들> (존재확신, 위치정확도, 관측거리)` | 주변차량만 |
| 10 | `※위치·속도 불확실` | 관측거리 40m 초과 또는 위치정확도 0.5 미만 |
| 11 | `[<기준차량> 기준 전방 Nm, 좌측 N.Nm]` | 기준차량 상대 위치 |

> **`존재확신` 과 `위치정확도` 는 다른 값이다.** 바로 앞의 차량은 존재가 확실하지만
> bbox 가 절단돼 위치가 부정확할 수 있다. 한 값으로 섞으면 앞차가 저신뢰로 보고된다.
> 궤적 절의 소절 머리글도 **같은 낱말**(`존재확신`)을 쓴다.

### 수록 대수와 절단 고지

`(전체 차량 26대 중 상위 26대 수록)` — 잘라냈으면 `, N대 생략)` 이 붙는다.
**생략을 반드시 본문에 적는다** — 모델이 "전부 봤다"고 오인하면 없는 차량에 대해
단정적 판단을 한다.

수록 대수는 관측량에 맞춰 정한다(관측된 전부, 하한 15·상한 40).

### 5-3. 상호작용 및 주의 상황

```
- V021 → V010 | 선행차 추종 | 간격 23.0m | 헤드웨이 2.7s | TTC 3.8s
- P023 → P009 | 교차로 J38, 도달시간차 1.6s | 직교 진입 상충 예상 | TTC 10.3s
```

| 종류 | 설명문 |
|---|---|
| 추종 | `선행차 추종` + 간격·헤드웨이·TTC |
| 교차 | `교차로 <id>, 도달시간차 Ns` + `직교 진입 상충 예상` 또는 `대향 좌회전 상충 가능 — 좌회전/유턴 확률…` |
| 차선변경 | `<N>차선 진입 경합` |

없으면 `- 특이사항 없음`. 수록된 차량 간의 상호작용만 담는다(잘라낸 차량이 한쪽이면
제외).

## 6. BEV 개략도

````
## BEV 개략도 (기준: EGO_ego_vehicle)
```
...............................
..................H............
...............@12.............
```
@=기준차량 | 축척: 세로 ±80m(전/후), 가로 ±40m(좌/우) | @=EGO_ego_vehicle/관측차량(+0,+0)  1=…
````

기준차량 중심의 텍스트 격자다. `@` 가 기준차량, 숫자·문자가 다른 차량이며 범례에
각 기호의 액터 id·클래스·상대 위치가 붙는다. 같은 칸에 둘 이상 오면 `격자중복` 으로
표시한다. 기준차량 방위가 미확정이면 절 전체를 생략한다(회전 기준이 없으면 격자가
무의미하다).

정밀한 값이 아니라 **공간 배치의 보조 표현**이다. 정확한 좌표는 3·5번 절에 있다.

## 블록 3 — 질문

```
위 5초 관측 구간(t=3~8초)을 근거로, **마지막 관측 시점 이후 미래 5초**의
사고 발생 가능성을 1초 구간별로 판단하십시오.

구간 정의 (k번째 구간 = 마지막 관측 시점 이후 (k-1, k] 초):
  k=1: (8, 9] 초
  …
  k=5: (12, 13] 초

각 구간 k=1..5 을 **모두** 답하십시오.
- 사고가 예상되지 않으면: accident_expected=false, involved_actor_ids=[], …
- 사고가 예상되면: accident_expected=true, …
- involved_actor_ids 에는 **액터 id** 를 쓰십시오 (관측차량은 EGO_ 로 시작, …)
- 판단에 영향을 준 데이터 한계가 있으면 data_limitations 에 적으십시오.
```

**구간 정의를 절대 시각까지 펼쳐 적는다.** `(k-1, k]` 규약을 질문·정답·채점이 모두
같은 정의로 쓰고, 경계가 모호해지지 않도록 반개구간으로 못박는다.

액터 id 규칙을 여기서 한 번 더 못박는 이유는 2번 절의 관측자 이름과 혼동되기
때문이다.

## system 프롬프트

세 부분이다.

1. **역할** — 협력형 자율주행(V2X) 교통 상황 분석 전문가.
2. **데이터 규약** — 좌표계·방위·차선번호, 존재확신과 위치정확도의 차이,
   `속도 미확정`이 정지가 아니라는 것, 예상경로 확률이 사전확률이라는 것,
   선형연장이 경로 예측이 아니라는 것, 진행방향 미확정의 뜻, 인프라가 참여자가
   아니라는 것, 관측 관계 절의 해석법, 그리고 **신호등·정지선·차선 표시가 없다**는 것.
3. **판단 원칙** — 데이터에 있는 액터 id 만 쓸 것, 근거를 관측된 기하·운동에 둘 것,
   위험을 과장해 모든 구간을 사고로 표시하지 말 것, 반대로 명확한 상충은 주저하지 말 것.

> **규약 문구는 본문 표기를 우선하고 JSON 필드명을 괄호로 병기한다** — 예:
> `'위치정확도'(position_quality)`. 구조화 JSON 블록이 기본 비활성이므로, 필드명만
> 쓰면 모델이 볼 수 없는 것을 가리키게 된다.

Claude 경로는 system 블록에 `cache_control` 을 두어 반복 호출 시 프리픽스를
캐싱한다 (윈도우별 본문은 캐시 브레이크포인트 뒤에 온다).

## 정답 누수 차단

자연어 브리핑에 **들어가지 않는** 것:

- 시나리오 id 의 분할명(`..._accident` / `..._normal`)
- 충돌 발생 여부·시각·주체
- 미래 구간의 어떤 정보도

payload 와 정답의 짝짓기는 **파일명**(`llm_payload_3-8.json` ↔
`ground_truth_3-8.json`)과 manifest 가 한다.

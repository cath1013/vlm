# LLM payload 생성 — 모듈별 알고리즘

payload 하나가 만들어질 때까지 어떤 모듈이 무엇을 계산하는지, **어떤 알고리즘으로**
하는지, 그리고 **왜 그렇게 정했는지**를 모듈 단위로 정리한다.

절차 순서로 읽고 싶으면 [전체 흐름](#전체-흐름)만 보고, 특정 모듈의 판정 규칙이
궁금하면 해당 절로 바로 간다. payload 의 자연어 부분이 어떤 절로 구성되는지는
[`payload_text_structure.md`](payload_text_structure.md) 에 따로 있다.

---

## 전체 흐름

```
데이터셋/영상 + 도로 지도
      │
      ▼  ① 관측 생성                    deepaccident.py / perception.py
   Detection (bbox + 카메라 이름 [+ 3D 측정값])
      │
      ▼  ② 역투영                       geometry.py          ← camera 모드만
   Observation (관측자 기준 (x_fwd, y_left))
      │
      ▼  ③ 월드 변환                    geometry.py / pipeline.py
   Observation (ENU (e, n))
      │
      ▼  ④ 다중 관측자 융합             fusion.py
   ActorState (전역 actor_id, 중복 제거)
      │
      ▼  ⑤ 도로·차선 매칭               roadmap.py
   RoadPlacement (도로, 차선번호, 진행방향, 교차로 거리)
      │
      ▼  ⑥ 운동학·기동                  kinematics.py
   속도, 가속도, 기동 라벨, 방위
      │
      ▼  ⑦ 경로 예측                    prediction.py + roadmap.py
   PredictedPath (기동, 확률, 웨이포인트)
      │
      ▼  ⑧ 상호작용·위험               kinematics.py
   Interaction (추종·교차·차선변경 상충, TTC)
      │
      ▼  ⑨ 스냅샷 조립                  pipeline.py
   SceneSnapshot (액터 + 상호작용 + 인프라 + 지도맥락)
      │
      ▼  ⑩ 윈도우 분할                  accident_qa.py
   TimeWindow (T초 관측 × stride 간격)
      │
      ▼  ⑪ 직렬화                       serialize.py + i18n.py
   자연어 브리핑 [+ 구조화 JSON] + 질문
      │
      ▼  ⑫ 요청 본문 조립               providers.py
   llm_payload_<구간>.json
```

| 모듈 | 단계 | 한 줄 요약 |
|---|---|---|
| `deepaccident.py` | ① | 데이터셋 레이블 → Detection. 카메라 열거, 카메라별 가시성 판정 |
| `perception.py` | ① | 검출기 인터페이스 (YOLO / 사전계산 JSON) |
| `geometry.py` | ②③ | 카메라 1대분 투영·역투영, 좌표 변환 |
| `fusion.py` | ④ | 여러 관측자의 같은 물체를 하나로 |
| `roadmap.py` | ⑤⑦ | 도로 매칭, 진행방향 판정, 하류 경로 열거 |
| `kinematics.py` | ⑥⑧ | 속도·방위 적합, 기동 분류, 상충 분석 |
| `prediction.py` | ⑦ | 하류 경로 → 시간축 웨이포인트 |
| `pipeline.py` | ③⑨ | 시각 동기화, 단계 순서, 지도 맥락 |
| `accident_qa.py` | ⑩⑪ | 윈도우 분할, 접근 쌍, 질문·정답·채점 |
| `serialize.py` | ⑪ | 자연어·JSON·ASCII BEV 생성 |
| `i18n.py` | ⑪ | 모델이 읽는 모든 문자열의 한국어/영어 |
| `providers.py` | ⑫ | Claude/OpenAI/Gemini 요청 본문 |

## ① 관측 생성 — `deepaccident.py`

**입력** 레이블 텍스트 + calib(pickle) + meta
**출력** `Detection` 목록 (프레임·트랙 id·클래스·bbox·카메라 이름 [+ 3D 측정값])

### 카메라 열거 (`available_cameras` / `resolve_cameras`)

calib 에서 `intrinsic_<이름>` 과 `lidar_to_<이름>` 이 **둘 다** 있는 카메라의
교집합을 취한다. 한쪽만 있으면 쓸 수 없다.

`DeepAccidentConfig.cameras=None`(기본)이면 전부를 쓴다. 이름 목록을 주면 그것만
쓰되, **calib 에 없는 이름은 예외로 막는다** — 오타 하나로 카메라가 조용히 빠지면
"측방 차량이 원래 안 보인다"는 잘못된 결론에 이른다.

DeepAccident 의 구성:

| 카메라 | yaw | 수평화각 |
|---|---|---|
| `Camera_Front` | 0° | 70° |
| `Camera_FrontLeft` / `Camera_FrontRight` | ±55° | 70° |
| `Camera_BackLeft` / `Camera_BackRight` | ±110° | 70° |
| `Camera_Back` | 180° | 110° |

합집합으로 방위 360°를 덮는다.

### 2단 필터

**1층 — 속성 필터 (카메라와 무관, 객체당 1회)**

| 판정 | 통계 키 |
|---|---|
| 자기 행(`id=-100`) 제외 | `dropped_self` |
| 추적 불가(`id=-1`) 제외 (기본) | `dropped_untracked` |
| 클래스 필터 | `dropped_class` |
| 사거리 초과 (120m) | `dropped_range` |
| `vis=False` (어느 카메라에도 안 보임) | `dropped_not_visible_any_cam` |
| 라이다 포인트 부족 (기본 미적용) | `dropped_lidar_pts` |

**2층 — 카메라별 기하 판정 ((객체, 카메라) 쌍마다)**

카메라마다 독립으로 돈다.

1. 3D 박스 8코너를 만들고(중심 + yaw 회전 + 반치수) `lidar_to_<카메라>` 로 그
   카메라 좌표계로 옮긴다.
2. 모든 코너의 깊이가 ≤ 0.5m 면 후방 → `dropped_behind`.
3. 앞쪽 코너만 `K` 로 픽셀에 찍고 **축정렬 외곽(min/max)** 을 취해 2D bbox 를
   만든다. 화면과 전혀 겹치지 않으면 → `dropped_outside_fov`.
4. 화면으로 클립한 뒤 폭·높이 < 12px → `dropped_small_bbox`.
5. **깊이 정렬 가려짐**: 가까운 것부터 10px 격자를 점유시키고, 남은 노출 면적
   비율이 0.35 미만이면 → `dropped_occluded`.

> **가려짐 격자는 카메라마다 따로 쓴다.** 화상면이 다르므로 격자를 공유하면
> 전방 카메라에서 앞차에 가려진 차량이 측방 카메라에서도 가려진 것으로 처리된다.

**한 대라도 본 객체를 남기고**, 여러 대가 봤으면 **노출 면적이 가장 큰** 카메라의
bbox 를 쓴다 — 화면 끝에서 절단된 bbox 보다 온전히 담긴 것이 역투영 정확도가
높다. 어느 카메라도 못 본 객체는 `dropped_no_camera`.

> **객체 단위 항등식**: `total_rows = 속성탈락 + kept + dropped_no_camera`.
> 기하 항은 (객체, 카메라) 쌍마다 세므로 더하면 전체 행 수를 넘는다.

Town05 실측 (전면 1대 → 6대): 검출 3,083 → **7,073**, `dropped_no_camera`
5,415 → **1,425**, 스냅샷당 관측 차량 15.2 → **21.5**대.

### 관측 모드

- **`sensor3d`**(기본) — 레이블의 3D 위치·yaw·(vx,vy)를 `Detection` 에 실어
  보낸다. 값은 그대로 쓰고, **무엇이 보이는지는 위 가시성 판정으로 정한다**.
  절대 월드좌표는 `ego_to_world @ lidar_to_ego` **전체 4×4** 로 구한다 —
  yaw 만으로 되돌리면 경사로에서 pitch/roll 성분이 빠져 어긋난다(실측 2.4m).
- **`camera`** — bbox 만 남기고 위치를 역투영으로 추정한다.

### 텔레메트리 합성 (`synthesize_telemetry`)

GPS 채널이 없어 자세에서 만든다. 위치는 자기 레이블 행의 **박스 중심**
(`ego_to_world` 평행이동 성분은 차량 기준점이라 박스 중심과 다르다), 방위는
`ego_to_world` 회전행렬, 속도는 레이블 1행(월드 프레임), yaw rate 는 방위 차분.

### 노면 고도 (`estimate_ground_z`)

레이블 박스 **밑면**에서 추정한다. 자기 행 우선 → 근거리 객체 중앙값 → 정지
센서는 여러 프레임 취합. 먼 객체를 섞으면 고도가 다른 지형에 끌려간다
(Town03 3.84m vs 실제 7.99m).

## ② 역투영 — `geometry.py`

`camera` 모드에서만 돈다. `CameraModel` 은 **카메라 1대분**이고, 관측자가 여러
대를 달면 카메라마다 하나씩 만든다.

### 알고리즘 (`bbox_to_ego`)

1. bbox 밑변 중점을 **접지점**으로 보고 광선을 만든다.
2. 평면 노면(z = −지상고)과의 교점을 구한다 (IPM).
3. **근접면 보정** — 차량은 점이 아니라 상자다. 접지점은 차량의 *뒷면*이 아니라
   카메라를 향한 *앞면* 이므로, 클래스별 길이 사전값의 절반을 더해 중심으로 옮긴다.
   극근접에서 보정량이 거리의 절반에 달한다.
4. bbox 폭과 클래스 폭 사전값으로 얻은 거리와 교차 검증해 `range_quality` 를 낸다.

> **지상고를 반드시 변환 사슬 전체로 계산한다.** 인프라는 높이가
> `ego_to_world[2,3]` 에 있고 `lidar_to_ego` 는 항등행렬이다. 후자만 보면 지상고가
> 0 이 되어 노면 교점이 원점으로 붕괴한다. `CameraModel` 은 지상고 ≤ 0 을 예외로
> 막는다.

실측 오차: 15~70m 에서 중앙값 2.0~2.5m, 70m 초과에서 7.3m.

## ③ 월드 변환 — `pipeline.py`

관측자 자세(위치·방위)로 차량좌표를 ENU 로 옮긴다.

**3D 센서가 절대 좌표를 주면 그것을 그대로 쓴다** (`world_xy_measured`).
`ego_xy_measured` 를 2D 회전으로 되돌리지 않는다 — 경사로에서 pitch/roll 성분이
빠진다.

### 카메라별 파라미터 선택

```python
ego_xy, quality = src.model_for(det.camera).bbox_to_ego(...)
```

`Detection.camera` 가 어느 카메라의 bbox 인지 알려 주고 `VehicleSource.model_for()`
가 짝을 찾는다. 모르는 이름은 기준 카메라로 떨어뜨린다(설정 오류로 파이프라인이
멈추는 것보다 낫다).

> **왜 중요한가.** 후방 카메라 검출을 전면 파라미터로 풀면 yaw 가 180° 틀려 차량이
> 반대편에 놓인다. camera 모드 실측 위치오차가 **중앙값 3.14m(올바른 파라미터) 대
> 22.55m(전면 일괄)**, p90 은 10.6m 대 120.8m 다. 검출 1,309개 중 878개가 전면 아닌
> 카메라의 것이므로 영향이 크다.

## ④ 다중 관측자 융합 — `fusion.py`

**입력** 여러 관측자의 `Observation`
**출력** 중복 제거된 `ActorState` + 전역 `actor_id`

### 게이팅

단안 측거 오차는 거리의 제곱에 가깝게 커진다. 고정 게이트를 쓰면 원거리에서 같은
차량이 둘로 갈라진다.

```
gate = min(6.0 + 0.14 × 관측거리, 25.0) + (거리신뢰도 낮으면 +4.0)
```

### 신원 판정 순서

1. **전역 트랙 id** (`global_track_ids=True`, **기본값**) — V2X 로 객체 id 를
   공유하는 전제다. 같은 id 면 **위치와 무관하게** 같은 물체이므로, 극근거리 측거
   오차로 한 차량이 둘로 갈라지지 않는다. DeepAccident 의 CARLA actor id 도 같은
   조건이다.

   전제가 깨지는 경우(카메라별 독립 추적기)를 대비해, 같은 id 로 묶인 관측이
   `id_collision_dist_m`(기본 150m)보다 흩어져 있으면 위치로 쪼개고
   `GlobalTrackRegistry.id_collisions` 를 올린다. 임계는 실측 산포에서 정했다 —
   id 가 진짜 전역인 `camera` 모드 클러스터의 위치 산포가 p99 39.9m·최대 66.0m
   이고, 진짜 충돌은 수백 m 다.
2. **클래스 호환성** — `CLASS_GROUP` 으로 `vehicle`(car/van/truck/bus/motorcycle)
   과 `vru`(bicycle/person)를 나눈다. 군이 다르면 병합하지 않는다.
   *보행자가 오토바이 트랙을 물려받아 27.8km/h 로 달리는 일이 있었다.*
3. **거리 최적 할당** — 남은 것들을 게이트 안에서 짝짓는다.

### 관측자 본체 흡수

관측자 A 가 검출한 것이 관측자 B 의 본체일 수 있다. 트랙 id 를 다 아는 경우
(`authoritative`)에는 id 로만 판정한다 — 거리 기반 흡수는 옆 차량까지 삼킨다.

### 대표값 선택

여러 관측이 같은 물체를 가리키면 **하나를 대표로 고른다. 평균하지 않는다.**
평균은 어느 센서도 관측하지 않은 값을 만들고, sensor3d 의 "GT 그대로" 전제를
깨뜨린다. 선택 기준은 `_freshest`: 최신 관측 우선, 같으면 가까운 관측.

## ⑤ 도로·차선 매칭 — `roadmap.py`

**출력** `RoadPlacement` (도로 id·이름, s, 횡오프셋, 진행방향, 차선번호,
교차로 거리, 도로축 방위)

### 도로 선택 (`locate`)

각 도로에 점을 정사영해 `거리 + 0.25 × 축정렬도` 가 가장 작은 도로를 고른다.
방위가 도로축과 70° 넘게 어긋나면 그 도로는 후보에서 제외한다.

### 진행 방향 판정 (`_is_reverse`) — 실측 신뢰도 순서

| 순위 | 근거 | 실측 반전율 |
|---|---|---|
| 1 | **실측 방위**(텔레메트리·3D 센서) | 0% |
| 2 | 일방통행 표기 | 19~25% |
| 3 | 통행측 (우측통행에서 주행차로는 중심선 오른쪽) | 7% |
| 4 | 단서 없음 → 정방향, `direction_confident=False` | — |

통행측은 **차도 폭 안**에 있을 때만 신뢰한다. CARLA 의 분리 도로는 방향별로 별개
road 이므로, 기준선에서 차도 폭을 넘어 떨어진 차량은 나란한 다른 도로에 속한다 —
반전율이 |횡오프셋| 7m 이하 2~12% 에서 7m 초과 **54%** 로 급증한다.

### 하류 경로 열거 (`downstream_paths`)

1. **진행 방향을 국소 도로축과 비교해 정한다.** 폴리라인 첫 구간과 비교하면
   곡선 도로에서 판정이 뒤집힌다 — 실측 22%의 경로가 방위와 180° 반대로 나갔다.
   `RoadPlacement.axis_bearing_deg`(locate 가 저장한 국소 축)를 쓴다.
2. **차량이 달리는 차로를 따라 샘플링한다** (5m 간격, `lateral_offset_m` 만큼
   평행이동). 중심선을 쓰면 경로가 차로 폭만큼 옆에서 시작한다(실측 5~10m).
3. 교차로에 닿으면 진출로마다 진출 방위를 재서 기동을 분류한다.

   | 상대 회전각 | 기동 | 기본 가중치 |
   |---|---|---|
   | \|turn\| < 30° | 직진 | 0.6 |
   | \|turn\| > 150° | 유턴 | 0.02 |
   | turn > 0 | 좌회전 | 0.2 |
   | 그 외 | 우회전 | 0.2 |

4. 차선 위치로 보정: 1차선(중앙선쪽)이면 좌회전 ×2.0 아니면 ×0.4, 최외측이면
   우회전 ×2.0 아니면 ×0.4.
5. **확률은 기동 단위**다. 한 기동으로 갈 수 있는 진출로가 여럿이면 그 기동의 몫을
   진출로 수로 나눈다 — 도로마다 독립 가중치를 주면 교차로가 오른쪽 진출로를 2개
   열어 두었다는 이유만으로 우회전이 좌회전의 2배가 된다.
6. 같은 (기동, 기하) 후보는 하나만 남긴다.

### 교차로 인식

도로 끝점을 클러스터링해 만든다. 3개 이상 도로가 만나면 `is_intersection`.

## ⑥ 운동학 — `kinematics.py`

### 하나의 적합, 두 개의 불확실도

궤적 표본에 **최소자승 직선**을 적합해 속도 벡터를 얻고, 불확실도를 **두 가지**로
낸다.

| 불확실도 | 계산 | 쓰이는 곳 |
|---|---|---|
| `sigma_v` | 적합 잔차 | 속도 **크기** 관문 |
| `sigma_pos` | 관측거리 기반 p90: `max(5.0, 0.06r + 0.0015r²)` | **방향** 관문 |

> **왜 둘로 나누는가.** 원거리 측거 편향은 **매끄럽게 드리프트**한다. 잔차는 작은데
> 방향은 180° 뒤집힌다. 잔차만 보면 그 뒤집힌 방향을 확신하게 된다.

### 세 개의 관문

1. **속도** — 추정 속도가 잔차의 2배에 못 미치면 미확정.
2. **클래스별 지속 주행 속도 상한** — 신원 관문(`max_speed_by_class`)과 **다른**
   값(`report_speed_by_class`)을 쓴다. 보행자는 신원 관문 8m/s, 보고 상한 2.5m/s.
   한 값으로 겸하면 위치 잡음이 "28km/h 로 달리는 보행자"로 나간다.
3. **방향** — 이동량이 `sigma_pos` 를 넘지 못하거나 관측거리가 70m 를 넘으면
   방위를 미확정으로 둔다.

### 방위의 출처

`telemetry`(GPS/IMU) → `measured`(3D 센서) → `trajectory`(궤적 미분) →
`road`(도로축). 궤적 미분 방위는 원거리에서 180° 뒤집히는 일이 흔해(레이블 yaw 대비
90° 초과가 10%), 도로에 매칭된 **차량**은 도로축으로 대체한다. 보행자·자전거는
차로를 따르지 않으므로 제외한다.

진행 방향을 모르면 방위를 **미확정**으로 둔다 — 절반의 확률로 180° 틀린 값을
내보내는 것보다 낫다.

### 기동 분류

차선 변경은 2.5초 관측창의 횡오프셋 변화로 판정하므로 **1~2초 지연**된다.
관측거리가 프레임 간 2m 이상 변하고 45m 초과인 구간에서는 가감속을 보고하지
않는다 — 편향 미분이 허위 급감속으로 나타난다.

### 상호작용 (`analyze_interactions`)

| 종류 | 판정 |
|---|---|
| `following` | 같은 도로·같은 차선, 앞뒤 관계, 헤드웨이·TTC |
| `crossing` | 같은 교차로로 향하는 두 차량의 도달시간차. 직교 진입 또는 대향 좌회전 상충 |
| `lane_change_conflict` | 차선변경 중인 차량의 목표 차선에 다른 차량 |

`risk_score` 는 TTC·거리·클래스로 액터 중요도를 매기고, 직렬화에서 수록 순서를
정한다.

## ⑦ 경로 예측 — `prediction.py`

**입력** `ActorState` + `RoadNetwork` + 지평(기본 3초)
**출력** `PredictedPath` 목록 (기동, 확률, 1초 간격 웨이포인트, 진입 도로, 잘림 여부)

1. 속도 미확정이면 **"경로 예측 보류"** 하나만 낸다 (정지로 단정하지 않는다).
2. 0.5m/s 미만이면 "정지 유지".
3. 도로 미매칭이면 등속 직진(방위 외삽).
4. `roadmap.downstream_paths` 로 후보 폴리라인을 얻는다.
5. **경로가 차량 위치에서 시작하도록** 폴리라인 앞에 현재 위치를 붙인다
   (0.5m 초과로 떨어져 있을 때).
6. `_resample_by_time` — 호길이 기준 1초 간격 재샘플링. **폴리라인이 지평보다
   짧으면 거기서 멈추고 `truncated=True`** 를 표시한다. 예전에는 마지막 점으로
   채웠는데, 같은 좌표 반복은 "그 자리에 정지한다"는 예측으로 읽힌다.
7. `_merge_identical` — 출력 해상도(0.1m)에서 기하가 같은 경로를 합치고 확률을
   더한다. CARLA 는 한 도로를 차로마다 별개 road 로 쪼개므로, 합치지 않으면
   라벨·확률·좌표가 똑같은 항목이 여러 개 나간다. 진입 도로는 `to_roads` 목록으로
   남긴다.

**이 확률은 도로 구조와 차선 위치에서 유도한 사전확률이다.** 방향지시등·제동등을
관측한 값이 아니다.

## ⑨ 스냅샷 조립 — `pipeline.py`

`snapshot_at(t)` 가 시각 t 의 `SceneSnapshot` 을 만든다. 단계 순서가 중요하다.

```
1) 1차 도로 매칭        (방위를 알기 전)
2) 운동학 갱신
3) 도로 재매칭          ← 방위를 알았으므로 진행방향 확정
4) 도로축 방위 채택
5) 기동 확정
6) 경로 예측
7) 상호작용 분석
```

**재매칭은 모든 액터에 한다.** 예전에는 `kind == "observed"` 만 했는데, 그러면
텔레메트리 방위를 가진 가장 정확한 관측차량이 그 근거를 못 쓴다 — 일방통행 도로에서
차도 폭을 벗어나면 진행방향이 실측 방위와 180° 어긋났다(실측 5/76).

### `reset()` 의 필요성

`run()` 은 시나리오를 처음부터 스트리밍하므로 매 호출에 누적 상태(신원 레지스트리,
궤적 이력)를 초기화한다. 하지 않으면 두 번째 호출이 첫 호출의 이력을 안은 채 t=0
부터 시작해 방위·속도 추정이 망가진다. *CLI 가 JSONL·윈도우·BEV 를 각각 다른
호출로 만들면서 조감도의 차량 방향이 도로와 어긋난 적이 있다.*

### 지도 맥락 (`map_ctx`)

도로/교차로 수, 관측자·인프라 id, 차선번호 규약, 통행측, 차선폭, 그리고
**관측자별 카메라 구성**을 담는다.

카메라 커버리지는 카메라별 `[yaw ± hfov/2]` 를 1° 격자에 **합집합**으로 채워
센다. 단순히 hfov 를 더하면 6대 × 70° = 420° 로 360°를 넘는다.

## ⑩ 윈도우 분할·질의 — `accident_qa.py`

### 윈도우 (`build_windows`)

길이 T(5초)를 stride(1초) 간격으로 밀며 자른다. 데이터가 부족한 윈도우는 버리고,
**충돌이 관측 구간 안에서 이미 일어난 윈도우도 버린다** — 예측 문제가 아니다.

시간 구간 규약: **k번째 구간 = 마지막 관측 시점 이후 (k-1, k] 초.** 질문·정답·채점이
모두 이 정의를 쓴다.

### 접근 쌍 (`closing_pairs`)

윈도우 첫 시각과 마지막 시각의 쌍 거리를 비교해 줄어든 쌍만 남긴다. 접근율
0.3m/s 미만, 선형 접촉시간이 지평의 3배 초과는 버린다.

**선형 접촉시간은 관측된 거리 변화율의 연장이며 경로 예측이 아니다.** 회전·제동을
반영하지 않는다.

### 수록 상한 — 관측량에 맞춘다

| 항목 | 규칙 | 하한 | 상한 |
|---|---|---|---|
| 수록 차량 | 관측된 전부 | 15 | 40 |
| 접근 쌍 | 차량 수 × 0.5 | 6 | 20 |

**고정 상한은 관측이 늘어날수록 담는 비율만 줄인다.** 카메라를 6대로 늘려 차량이
24→26대, 접근 쌍이 43→88개가 됐을 때 상한 6 고정이 **사고 당사자 쌍을 목록 밖으로
밀어냈다** — 모델이 놓친 게 아니라 payload 에 없었다.

여기에 순위와 무관한 안전장치가 있다. **접촉이 임박한 쌍은 상한을 넘겨도 담는다** —
`linear_contact_s` 가 질문 지평의 절반(2.5초) 이하면 순위를 무시한다.

실측(Town05, 충돌 t=9.2s)에서 당사자 쌍 순위는 충돌이 가까워질수록 단조롭게
개선된다: 46/85 → 22/95 → 8/88 → 2/91 → 1/80.

### 관측 관계 (`perception_summary`)

액터별 `observed_by` 를 **관측자 기준으로 뒤집는다**. 파생 가능한 정보를 중복해
담는 이유는, 이 역변환이 V2X 추론의 핵심인데 액터 수십 개에 흩어진 관계를 모델이
직접 뒤집으면 자주 틀리기 때문이다.

관측자마다 `observed_now`(자기 자신 제외), `only_this_observer`(혼자 본 차량 =
남의 사각지대를 메운 몫), `n_observed_in_window`, 카메라 대수·커버리지, 그리고
**본체 액터 id** 를 낸다.

> 본체 액터 id 가 필요한 이유: 관측자 이름(`ego_vehicle`)과 그 본체의 액터
> id(`EGO_ego_vehicle`)는 다른 문자열이다. 매핑이 없으면 모델이 답변에 관측자
> 이름을 써서 차량 지목이 전부 오답 처리된다(실제 호출에서 그랬다).

### 채점 (`score_response`)

구간별 TP/FP/TN/FN 과 차량 단위 재현율을 낸다. 융합이 한 차량을 여러 actor id 로
쪼갰을 수 있으므로 **그중 하나만 지목해도 맞은 것으로** 본다.

**응답 형식 검사** (`response_issues`) — `duplicate_k` / `missing_k` /
`unexpected_k` / `missing_k_field`. 채점은 k 로 짝지으므로 중복은 조용히 무시되고
누락은 정답이 '사고'일 때만 FN 이 된다 — 형식 오류가 점수에 거의 드러나지 않는다.

> JSON Schema 제약(`minItems`/`maximum`)으로 막지 **않는다**. OpenAI strict 모드가
> 그 키워드를 지원하지 않아 provider 별로 스키마가 갈린다. 항목 간 유일성은 애초에
> JSON Schema 로 표현할 수 없다.

## ⑪ 직렬화 — `serialize.py` / `i18n.py`

### 세 표현

| 함수 | 산출물 | 용도 |
|---|---|---|
| `to_text` | 자연어 브리핑 | LLM 추론 입력 (기본) |
| `to_json` | 구조화 JSON | 툴 호출·정량 파싱 (**기본 비활성**) |
| `to_bev_ascii` | 텍스트 조감도 | 공간 관계 보조 |

절 구조는 [`payload_text_structure.md`](payload_text_structure.md) 참고.

### 수록 차량 선택 (`rank_actors`)

`risk_score` 상위 N대만 담고 **잘라낸 대수를 본문에 명시한다** — LLM 이 "전부
봤다"고 오인하지 않도록.

### 확률 표시 반올림 (`_round_probs`)

각각 독립으로 반올림하면 표시값 합이 1 을 벗어난다(0.3417 × 3 = 1.02). 내부 계산은
정확히 1.0 인데 payload 만 어긋나 보이면 확률 자체를 못 믿게 된다. **최대잉여법**
으로 맞춘다.

### i18n 설계

파이프라인이 데이터 모델에 저장하는 라벨의 **정본은 한국어**이고, 직렬화 시점에
번역한다. 파이프라인 내부를 키로 바꾸면 로직·테스트가 전부 흔들리는데 얻는 것이
없다 — 라벨은 이 패키지만 생성하는 닫힌 집합이고 번역은 출력 경계 한 곳에서만
필요하다. 사전에 없는 값(도로명 등)은 그대로 통과시킨다.

### 정답 누수 차단

- 시나리오 id 는 분할명(`..._accident`)을 담으므로 **불투명 토큰**(SHA1[:12])으로
  치환한다.
- 충돌 정보는 payload 에 넣지 않는다.
- payload↔정답 짝짓기는 **파일명과 manifest** 가 한다.

## ⑫ 요청 본문 조립 — `providers.py`

**payload 파일 = 요청 본문 그대로.** 그래야 `**payload` 로 바로 보낼 수 있고 API 가
모르는 키가 섞이지 않는다.

| | Claude | OpenAI | Gemini |
|---|---|---|---|
| 엔드포인트 | `/v1/messages` | `/v1/chat/completions` | `models/{model}:generateContent` |
| system | `system[]` (+`cache_control`) | `messages[0]` role=system | `systemInstruction.parts` |
| 사용자 입력 | 블록 유지 | 한 문자열로 합침 | `parts[]` 유지 |
| 출력 제약 | `output_config.format.json_schema` | `response_format.json_schema` (strict) | `generationConfig.responseSchema` |
| 토큰 상한 | `max_tokens` | `max_completion_tokens` | `generationConfig.maxOutputTokens` |
| 모델 위치 | 본문 | 본문 | **URL 경로** |

**내용은 provider 와 무관하게 같다** (테스트로 고정). Gemini 는 모델이 URL 경로에
들어가므로 본문에 `model` 을 넣지 않고, provider·모델·엔드포인트는 manifest 에
기록한다.

응답 스키마의 정본은 JSON Schema 이고 Gemini 용은 OpenAPI 부분집합으로 옮긴다 —
`type` 대문자화, `additionalProperties` 제거, `propertyOrdering` 추가.

**모델 id 를 짐작하지 않는다.** Claude 만 검증된 기본값(`claude-opus-5`)이 있고
OpenAI·Gemini 는 `--model` 을 요구한다.

`max_tokens` 기본값은 **32000** 이다. 적응형 추론이 이 예산을 함께 쓰므로 넉넉해야
한다 — 16000 으로는 실제 호출에서 추론이 예산을 다 먹고 JSON 이 중간에 잘렸다
(`stop_reason=max_tokens`, 출력 16000 토큰 중 본문 1,410자만 남음).

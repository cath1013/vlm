# deepaccident_replicate — 돌아가는 비교 대상

`traffic_llm` 의 사고 예측을 무엇과 비교할 것인가. 논문의 대상은 DeepAccident 의
사고 예측(V2XFormer + 후처리)이지만 **공개된 것을 그대로 돌릴 수 없어** 방법을 다시
구현했다. 이 패키지는 `traffic_llm` 에 의존하고 그 반대는 아니다 — 비교 대상이 본체를
오염시키지 않게 한 방향으로만 묶어 둔다.

| 파일 | 무엇 | 학습 |
|---|---|---|
| `da_baseline.py` | 사고 **판정 규칙** 이식 (거리 임계 하나) | 불필요 |
| `da_motion.py` | 판정을 먹이는 **운동 예측 모델** (BEV 흐름 + 사고 헤드) | 필요 |
| `train_da_motion.py` | 프레임 캐시 + 학습 | |
| `eval_da_motion.py` | 평가 — `score_modes` 를 통과해 LLM 과 같은 표에 오른다 | |

테스트는 저장소 관례대로 `tests/test_da_baseline.py`, `tests/test_da_motion.py` 에 있다.

---

논문의 비교 대상은 DeepAccident 의 사고 예측(V2XFormer + 후처리)이다. **공개된 것을
그대로 돌릴 수는 없다.** 두 가지가 각각 독립적으로 막는다.

| 막는 것 | 근거 |
|---|---|
| 가중치 미배포 | `README.md` 의 Model Zoo 절이 통째로 주석 처리(`[//]: # (## Model Zoo)`). 살아 있는 링크 둘은 지표가 mAP/NDS/Map IoU 인 **nuScenes 용 BEVDet** 가중치다 |
| 빌드 불가 | 원본은 Python 3.7 / PyTorch 1.10.2 / **CUDA 10.2** / mmcv-full 1.3.14. CUDA 10.2 의 최대 아키텍처는 sm_75 인데 이 머신의 GPU 는 **sm_120**(Blackwell) 이다 |

설령 학습해도 논문 Table 3·4 는 재현되지 않는다 — 공개된 융합 모듈은 CoBEVT 가 아니라
평균 풀링이다 (`basic_modules.py:637` 에서 조기 return, 그 아래는 죽은 코드).

그래서 **두 층으로 나눠 이식했다.**

| 모듈 | 무엇 | 학습 필요 |
|---|---|---|
| `da_baseline.py` | 사고 **판정 규칙** (거리 임계 하나) | 없음 |
| `da_motion.py` | 사고 판정을 먹이는 **운동 예측 모델** | 있음 (`examples/train_da_motion.py`) |

## 판정 규칙 (`da_baseline.py`)

원본 코드에서 읽어온 값을 그대로 잠갔다 (`tests/test_da_baseline.py`).

| 항목 | 값 | 출처 |
|---|---|---|
| 예측 쪽 거리 임계 | 5 px × 0.5 m/px = **2.5 m** | `multi_gpu_test.py:527` |
| 비교 연산 | `preddist < threshold` (강부등호) | `:583` |
| 기본 지평 | 2.0 초 (2 Hz × 4 프레임) | `configs/DeepAccident_tiny.py` |
| 채점 프레임 | **마지막 하나만** (원본 버그) | `:553` — 루프 안에서 초기화, 밖에서 소비 |

논문 본문은 임계를 "1.0 m" 라 하지만 코드는 2.5 m 다. **코드를 따랐다** — 재현 대상은
발표된 숫자를 만든 코드다.

변형 넷을 함께 낸다. 한 번에 하나씩만 바꾼다: `da`(코드 그대로) · `da_any`(논문
서술대로 지평 내 아무 시점) · `da_h5`(우리와 같은 5초 지평) · `da_fit`(임계값을 train
에서 적합 — 저자들의 상수만 쓰면 규칙을 불리하게 만든 비교가 된다).

## 운동 예측 모델 (`da_motion.py`)

원본의 motion head 형태를 옮겼다. **좌표를 액터별로 회귀하지 않는다** (그것은
`predict_nets.WaypointNet` 이다). 장면 전체를 BEV 래스터로 보고 **픽셀별 미래 흐름**을
낸다 — FIERY/IterativeFlow 계열이고 DeepAccident 가 쓰는 방식이다. 액터의 미래 위치는
그 액터 픽셀의 흐름을 평균해 얻는다. 장면을 함께 보므로 차들이 서로를 통과하는 예측이
억제된다.

| 항목 | 값 | 출처 |
|---|---|---|
| BEV 격자 | ±50.0 m @ 0.5 m/px → 200×200 | `DeepAccident_tiny.py` motion grid |
| 관측 → 예측 | 과거 3 프레임 → 미래 4 프레임 (@2 Hz) | 같은 config |
| 표본 | 5개 + 분포 평균 = **6개**, 마지막이 평균 | `_base_motion_head.py:315-320` |
| 사고 판정 | 표본 **아무거나** 접촉하면 사고 | 논문 "prioritizing safety" |
| 대상 클래스 | 차량만 (보행자·자전거 제외) | `ConvertMotionLabels(only_vehicle=True)` |

```bash
# 1) 프레임 캐시 (NFS 대역폭에 묶인다 — 한 번만)
.venv/bin/python examples/train_da_motion.py cache \
    --root /home/sryu/inclab-nas/DeepAccident --split train \
    --out out/da_motion/frames_train.npz

# 2) 학습
.venv/bin/python examples/train_da_motion.py train \
    --train-cache out/da_motion/frames_train.npz \
    --val-cache out/da_motion/frames_val.npz

# 3) 평가 — 같은 채점기(score_modes)를 통과해 LLM 과 같은 표에 오른다
.venv/bin/python examples/eval_da_motion.py \
    --root /home/sryu/inclab-nas/DeepAccident --split val \
    --model out/da_motion/da_motion_best.pt
```

캐시는 래스터가 아니라 **액터 배열**을 담는다 (표본당 몇 KB). 200×200×5 래스터를
미리 저장하면 표본당 5 MB 라 감당이 안 된다.

## 입력이 카메라가 아니다 — 논문에 반드시 적어야 한다

원본은 6카메라 × 5에이전트 영상을 받는다. 이 재구현은 **라벨에서 래스터화한 BEV** 를
받는다. 의도적이다: 우리 파이프라인도 같은 라벨을 "각 차량이 센서로 취득한 정보" 로
쓰므로, 두 방법에 **같은 인지**를 주고 예측·판정 방법만 다르게 하는 통제 비교가 된다.
카메라 프론트엔드는 이 위에 얹으면 되고, motion head 와 사고 후처리는 그대로 쓰인다.

## 이미 붙어 있는 쌍은 후보에서 뺀다

DeepAccident 라벨에는 **주차·정차 차량의 박스가 서로 겹쳐 있다** — 중심거리 3~4 m 인데
차 길이가 4.5~5.4 m 라 물리적으로 관통 상태다. 그 쌍을 후보로 두면 "모든 쌍의 최소
간격" 이 영구히 0 이라 어떤 거리 임계도 판정을 못 한다.

실측 (val 816창):

| | 5초 지평 최소 간격 0 | < 2.5 m |
|---|---|---|
| 등속 외삽 | 93 % | 99.9 % |
| 예측 경로(WaypointNet) | 93 % | 99.8 % |
| **기록된 실제 미래** | **86 %** | — |

기록된 미래에서도 그러므로 **예측 탓이 아니라 라벨의 성질**이다. 사고 예측은 벌어져
있다가 닫히는 쌍의 문제이므로, 관측 시점에 이미 접촉한 쌍을 빼는 것이 맞다
(`--exclude-touching`, `track_gaps(exclude_touching_now=True)`). 이 필터 없이 나온
`da*` 줄은 **정확도가 아니라 기저율**이며, `report_da_saturation()` 이 그것을 표와 함께
강제로 출력한다.

## 실측 결과 — 규칙이 이 데이터에서 판정을 못 한다

학습은 잘 된다 (val 흐름 L1 **1.89 m** @ 2초 지평). 그런데 **사고 판정 규칙이 어떤
임계값에서도 변별력이 없다.** val 816창, 임계값 스윕(바이너리 축):

| 임계 [m] | 발화율 | 정확도 | 균형정확도 |
|---|---|---|---|
| 0.00 | 0.000 | 0.634 | 0.500 |
| **0.10** | 0.721 | 0.479 | **0.541** ← 최대 |
| 1.00 | 0.800 | 0.445 | 0.527 |
| 2.50 (원본 값) | 0.883 | 0.399 | 0.501 |
| 5.00 | 0.923 | 0.382 | 0.494 |

균형정확도 최대가 0.541 이다 — 우연(0.500)과 거의 같다. 임계값 0 에서 0.1 로 올리는
순간 발화율이 0 → 0.72 로 뛴다.

**원인은 모델이 아니라 판정에 쓰는 양이다.** "모든 쌍의 최소 폴리곤 간격" 은 이
데이터에서 포화된다. 원본 라벨(단일 에이전트, 정지쌍 제외)로 잰 **기록된 미래 2초**:

| 임계 | 걸리는 표본 |
|---|---|
| < 0.01 m (실제 접촉) | **13.5 %** |
| < 2.5 m (원본의 예측 임계) | **89.2 %** |

중앙값 최소 간격이 1.34 m 다. **2.5 m 차체 간격은 그냥 정상 주행이다** — 교차로에서
옆 차선 차와 스치는 거리다. 모델 예측이 완벽해도 이 임계로는 판정이 안 된다.

이것은 원본 지표의 성질과 맞물린다: 저자들은 GT 쪽에 `dist_threshold_gt = 0.001` px
(사실상 접촉)를 쓰고 예측 쪽에만 2.5 m 를 쓴다 (`multi_gpu_test.py:526-527`). 그 느슨함은
모델 오차를 흡수하려는 것인데, 그들의 BEV 모델은 ego 근처의 소수 인스턴스만 내놓는
반면 우리는 장면의 모든 차량 쌍에 적용하므로 포화된다.

**우리 인지가 그것을 더 악화시킨다.** 같은 시각에서 겹치는 프레임 비율이 원본 라벨은
31 % 인데 융합된 `sensor3d` 액터는 **52 %** 다. 액터 수는 같고(중앙값 12) 중복도 거의
없다(중심거리 <1.5 m 인 쌍 1/18,991). 즉 개수나 중복이 아니라 **위치 오차**가 인접
차량을 겹치게 만든다.

정리하면 이 비교를 의미 있게 만들려면 판정에 쓰는 양을 바꿔야 한다 — 모든 쌍의 최소
간격이 아니라 **모델이 지목한 충돌 쌍**을 봐야 한다. 그것이 원본이 자기 설정에서
실제로 하는 일이다.
